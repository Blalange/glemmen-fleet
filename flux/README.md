# Flux

GitOps for the Talos cluster, replacing Fleet. Flux is bootstrapped into
`flux/clusters/glemmen/` and syncs everything from this repository.

## Layout

```
scripts/flux/
├── setup.py                    bootstrap Flux (GITHUB_TOKEN + KUBECONFIG)
└── manage.py                   status / sync / suspend / resume helpers

flux/
├── clusters/glemmen/           entry points, synced by the root Kustomization
│   ├── flux-system/            (generated by `flux bootstrap`)
│   ├── infrastructure.yaml     -> flux/infrastructure
│   ├── rook-ceph.yaml          -> rook-ceph cluster, CSI and resources
│   ├── cert-manager-issuers.yaml    -> cert-manager/issuers (chart -> issuers)
│   ├── cert-manager-certificates.yaml -> cert-manager/certificates (-> kube-system)
│   ├── ingress.yaml            -> flux/ingress (Traefik, depends on certificates)
│   ├── monitoring.yaml         -> flux/monitoring (KPS, Thanos, smartctl, iDRAC, unpoller)
│   ├── logging.yaml            -> flux/logging (Loki + Alloy log collection)
│   ├── network-mesh.yaml       -> flux/monitoring/network-mesh (host-network probe, wait: false)
│   ├── pxe.yaml                -> flux/infrastructure/pxe (proxyDHCP/TFTP + Talos boot assets)
│   ├── monitoring-dashboards.yaml / monitoring-alerts.yaml
│   └── apps.yaml               -> flux/apps (application Kustomizations)
├── infrastructure/             namespaces, cert-manager, external-dns, MetalLB, metrics-server, descheduler, YugabyteDB, Rook Ceph, NFD, GPU operator, PXE chainloader
├── ingress/                    Traefik HelmRelease + values
├── monitoring/                 kube-prometheus-stack, Thanos, smartctl-exporter, idrac-exporter, network-mesh, unpoller
├── logging/                    Loki (single replica) and the Alloy log collector
└── apps/                       Kustomization objects, Homepage, NetBox + inventory sync, media stack, Minecraft servers (Radar)
```

The application manifests themselves stay in the repository root (`colibri/`,
`energisjappa/`, `frigate/`, `homepage/`, `panel/`, `unifi/`,
`cert-manager/`, `kube-prometheus-stack/`) — the Flux Kustomizations point at
those directories. The old `fleet.yaml` files and the values files that moved
into `flux/` have been deleted.

Helm values live next to their HelmRelease and are turned into ConfigMaps with
`configMapGenerator`; the HelmRelease reads them through `valuesFrom`.

## Daily use

```sh
./scripts/flux/manage.py status                  # everything at a glance
./scripts/flux/manage.py sync                    # pull the latest Git revision now
./scripts/flux/manage.py reconcile homepage      # re-apply one Kustomization
./scripts/flux/manage.py apps-off                # suspend application workloads
./scripts/flux/manage.py apps-on                 # resume them
./scripts/flux/manage.py freeze / unfreeze       # suspend/resume everything
```

`flux reconcile` / `flux get` / `flux logs` also work directly if you prefer.
The pinned `flux`/`kubectl` binaries live in `scripts/bin/`; download them with
`./scripts/download-tools.py` (see `scripts/README.md`).

Tuppr's Talos/Kubernetes upgrade targets are generated from
`talos/settings.env`; use `./scripts/check-updates.py` to see available
Talos, Kubernetes, Flux, Helm and container-image updates.

## PXE boot

`infrastructure/pxe/` provides the network chainloader for nodes whose firmware
cannot boot the installed disk directly (for example, Talos on a PCIe NVMe
drive that is not exposed as a boot device). It consists of:

- a host-network `dnsmasq` proxyDHCP/TFTP pod, pinned to a control-plane node,
  which serves `undionly.kpxe` to BIOS clients and `ipxe.efi` to UEFI clients;
- a generated `boot.ipxe` that matches known nodes by SMBIOS serial, UUID or
  MAC and loads the current Talos kernel/initramfs;
- a small nginx asset server on the shared MetalLB VIP
  `http://192.168.6.99:8080` serving the kernel, initramfs and boot script.

Known Talos nodes boot the installed Talos system if one exists, otherwise they
enter maintenance mode with their static maintenance address. Unmatched
machines get a fallback menu offering netboot.xyz or a generic Talos
maintenance-mode boot. No machine configs or secrets are served; apply a config
with `./scripts/talos/manage.py apply <node>` after a node boots in maintenance
mode.

UniFi must continue to be the only DHCP address server, but its own PXE
boot filename/next-server options must be cleared so they do not conflict with
proxyDHCP. Machine identities live in `talos/pxe.yaml`; regenerate
`boot.ipxe` with `./scripts/talos/gen-pxe.py` after changing a node's network
configuration or selectors. See `infrastructure/pxe/README.md` for the full
runbook.

## NVIDIA GPU Operator

`infrastructure/gpu-operator/` deploys the NVIDIA GPU Operator from the NGC
Helm repository (`v26.7.2`). Talos supplies the kernel driver and userspace
libraries as system extensions, so the chart runs with `driver.enabled=false`
and `nfd.enabled=false`; it reuses the cluster's NFD release (which allows the
`nvidia.com` label namespace) and installs the container toolkit under
`/var/lib/nvidia`. CDI/NRI injection is enabled, so workloads request GPUs with
a `nvidia.com/gpu` limit and do not set a `runtimeClassName`.

The only GPU node is `glemmen250` (`glem.men/gpu=true`). Its Talos machine
config loads the `nvidia*` modules, and the extensions are built into the
schematic. Check the stack with:

```sh
kubectl get clusterpolicy
kubectl get pods -n gpu-operator
kubectl get node glemmen250 -o jsonpath='{.status.allocatable.nvidia\.com/gpu}'
```

Jellyfin requests **both** GPUs (`nvidia.com/gpu: 2`). With the 595.91.07
driver in the Talos v1.14.5 GPU extension, NVENC/NVDEC initialization fails
with `CUDA_ERROR_NO_DEVICE` when a container sees only some of the host's GPUs;
CUDA compute and `nvidia-smi` still work. Passing both GPUs is the workaround
until Talos ships the 610.x driver series, where the bug is fixed
(`NVIDIA/nvidia-container-toolkit#1249`,
`NVIDIA/k8s-device-plugin#1282`). Revert Jellyfin to one GPU after that
upgrade.

The operator's DCGM exporter ServiceMonitor is picked up by the cluster
Prometheus. Driver versions are tied to the Talos release; when upgrading
Talos, rebuild the schematic and roll the installer image (see
`talos/README.md`).

## Ceph object storage (RGW)

Long-term metrics and Loki logs live in the Ceph RGW object store managed by
Rook in `infrastructure/rook-ceph/`. RGW is exposed in-cluster at
`rook-ceph-rgw-fast.rook-ceph.svc.cluster.local:80` (Service
`rook-ceph-rgw-fast` in `rook-ceph`). The `fast` CephObjectStore uses RF2
metadata/data pools on the CMR OSDs; its pools are preserved on delete.

The `thanos` and `loki` buckets were created once with the RGW credentials and
are owned by the `CephObjectStoreUser` users of the same names. Rook generates
the key pairs in `rook-ceph-object-user-fast-thanos` and
`rook-ceph-object-user-fast-loki` (keys `AccessKey`/`SecretKey`). The buckets
are not recreated by Flux; they persist as long as the RGW pools do.

The clients read hand-created Secrets in `monitoring`, not Git:

```sh
ACCESS_KEY="$(kubectl -n rook-ceph get secret rook-ceph-object-user-fast-thanos \
  -o jsonpath='{.data.AccessKey}' | base64 -d)"
SECRET_KEY="$(kubectl -n rook-ceph get secret rook-ceph-object-user-fast-thanos \
  -o jsonpath='{.data.SecretKey}' | base64 -d)"

kubectl -n monitoring create secret generic thanos-objstore-config \
  --from-literal=objstore.yml="$(cat <<EOF
type: S3
config:
  bucket: thanos
  endpoint: rook-ceph-rgw-fast.rook-ceph.svc.cluster.local:80
  region: us-east-1
  access_key: ${ACCESS_KEY}
  secret_key: ${SECRET_KEY}
  insecure: true
  bucket_lookup_type: path
EOF
)" --dry-run=client -o yaml | kubectl apply -f -
```

For Loki, use the `rook-ceph-object-user-fast-loki` Secret and create
`loki-s3` with `LOKI_S3_ACCESS_KEY`/`LOKI_S3_SECRET_KEY` (the chart expands
those env vars into its S3 config):

```sh
ACCESS_KEY="$(kubectl -n rook-ceph get secret rook-ceph-object-user-fast-loki \
  -o jsonpath='{.data.AccessKey}' | base64 -d)"
SECRET_KEY="$(kubectl -n rook-ceph get secret rook-ceph-object-user-fast-loki \
  -o jsonpath='{.data.SecretKey}' | base64 -d)"

kubectl -n monitoring create secret generic loki-s3 \
  --from-literal=LOKI_S3_ACCESS_KEY="${ACCESS_KEY}" \
  --from-literal=LOKI_S3_SECRET_KEY="${SECRET_KEY}" \
  --dry-run=client -o yaml | kubectl apply -f -
```

The existing Thanos and Loki data was copied from the retired SeaweedFS S3
gateway with rclone before the clients were switched. The RGW data pool is
replicated on the fast tier for now; it can move to the bulk EC pools when
glemmen80 has its disks. The bucket names and client configuration stay the
same.

## Media stack

`apps/media` runs Jellyfin, Sonarr, Radarr, Prowlarr, Seerr, FlareSolverr and qBittorrent in
the privileged `media` namespace. The apps share one CephFS `ReadWriteMany`
volume at `/data` (`media-data-ceph`, `fast-fs`, 2300Gi) with `downloads/`,
`media/movies/` and `media/tv/`. The migration copied the qBittorrent downloads
and the existing Hærry Pot movie; the rest of the library was re-imported from
`/data/downloads` by Radarr and Sonarr as hardlinks, so it is present under
`/data/media` without duplicating Ceph data. Move the claim to `bulk-fs` when
glemmen80 has its disks. See [`apps/media/README.md`](../apps/media/README.md)
for the secrets, CephFS migration, Authentik provider setup and first-run
steps.

- **Databases:** all media apps use SQLite on their Ceph RBD config volumes.
  YSQL was evaluated for Sonarr/Radarr/Prowlarr, but their
  `DatabaseVersionParser` cannot parse YB's `server_version` string
  (`15.12-YB-...`). Jellyfin has no supported PostgreSQL backend, and Seerr's
  TypeORM migrations do not complete reliably on YSQL.
- **VPN:** qBittorrent shares its pod with gluetun. The Windscribe WireGuard
  profile lives only in the hand-created `qbittorrent-wireguard` Secret.
  Gluetun's firewall blocks all non-VPN egress.
- **SSO:** Jellyfin uses the SSO-Auth plugin and the existing Authentik
  `jellyfin` OAuth2 provider. The other apps are proxied by an in-cluster
  Authentik outpost connected to `https://auth.blalange.org`; Sonarr, Radarr,
  Prowlarr and qBittorrent run with application authentication `External`.
- **Backups:** the media library lives on CephFS and is treated as
  re-downloadable; it has no off-cluster backup. Ceph RF2 protects against a
  single OSD or host failure. The media app config volumes are on Ceph
  `fast-rbd`; there is no off-cluster volume backup yet.

## Thanos and long-term metrics

Prometheus runs two replicas for high availability. Each replica is capped at
15GiB of local TSDB blocks (`retentionSize` in
`monitoring/kube-prometheus-stack/values.yaml`), so each 20Gi PVC stays within
the 20GB usage budget. The operator gives the replicas different
`prometheus_replica` external labels, and Thanos Query deduplicates on that
label (the chart default), so Grafana does not see duplicate series. The Thanos
sidecar uploads completed blocks to the `thanos` bucket in Ceph RGW; the
`thanos` HelmRelease runs Query, Store Gateway and Compactor against the same
bucket. Grafana uses Thanos as its only Prometheus-compatible data source,
because it serves both live Prometheus data and the long-term blocks; the
chart's built-in Prometheus data source is disabled and deleted, and every
dashboard queries Thanos directly.

The Thanos component dashboards (Overview, Compact, Query, Query Frontend,
Store, Receive, Sidecar, Rule and BucketReplicate) live in
`monitoring/resources/dashboards/thanos/` and are refreshed by
`scripts/update-grafana-dashboards.py`. Node Exporter and UniFi Poller
dashboards live in sibling `node-exporter/` and `unifi/` directories. Their
ConfigMaps carry a `grafana_folder` annotation, and the Grafana sidecar plus
the file provider's `foldersFromFilesStructure` setting place them in
dedicated "Thanos", "Node Exporter" and "UniFi Poller" folders. The chart's
built-in Kubernetes-mixin and node-exporter-mixin dashboards get the same
annotation from the HelmRelease post-renderer. Dashboards without the
annotation stay at the root (General) level.

The Ceph and YugabyteDB dashboards live in the sibling `ceph/` and
`yugabyte/` directories. Ceph metrics come from the mgr Prometheus module
(scraped by `monitoring/resources/servicemonitors/ceph-mgr.yaml`) and the Rook
ceph-exporter ServiceMonitor; the dashboards are the upstream Ceph mixin
dashboards. The YugabyteDB dashboard is a trimmed copy of the upstream one:
YEDIS is disabled, and the ServiceMonitor drops every per-tablet series
(`table_id`) to avoid ingesting roughly 300k active series. The remaining
YB-Master and YB-TServer RPC metrics are relabeled to the `rpc_latency_*`
names the dashboard uses.

Create the `thanos-objstore-config` Secret from the Rook RGW user credentials
(see the Ceph object storage section above) before reconciling monitoring;
otherwise the Prometheus sidecar cannot start.

Then reconcile monitoring:

```sh
./scripts/flux/manage.py reconcile monitoring
kubectl -n rook-ceph get pods -l app=rook-ceph-rgw
kubectl -n monitoring get pods -l app.kubernetes.io/part-of=thanos
```

`PrometheusPVCAbove20GB` fires if the local volume stays above the budget.
The usual cause is the sidecar not uploading (check the `thanos` container in
the Prometheus pod) or the Prometheus retention update not being applied
(HelmRelease values are watched through the generated ConfigMap label).

The PVC of an existing cluster may already have been expanded beyond 20Gi;
Kubernetes cannot shrink it in place. The usage cap still applies. Shrinking it
is a separate maintenance operation: stop Prometheus, copy the data into a new
20Gi PVC with `pv-migrate`, and point the StatefulSet at the new claim. Only do
this after the sidecar has uploaded the local blocks that should be kept. See
[`scripts/README.md`](../scripts/README.md#persistentvolumeclaims) for the
`pv-migrate` workflow and download instructions.

## Loki and log collection

Loki stores logs in the `loki` bucket in Ceph RGW and runs as a single
binary (Monolithic) with one replica and one gateway
(`logging/loki/values.yaml`). Chunks and the TSDB index live in object storage;
the Loki pod keeps a 20Gi WAL/cache volume on the `nvme-rbd` StorageClass.
Retention is 30 days, enforced by the compactor. The chart's
component-specific dashboards (reads/writes/backend) are mostly empty in
Monolithic mode; the "Loki / Logs" and "Loki / Operational" dashboards are the
useful ones.

The S3 key pair is generated by Rook in
`rook-ceph-object-user-fast-loki`. Copy it into the hand-created `loki-s3`
Secret in `monitoring` before reconciling the logging Kustomization:

```sh
ACCESS_KEY="$(kubectl -n rook-ceph get secret rook-ceph-object-user-fast-loki \
  -o jsonpath='{.data.AccessKey}' | base64 -d)"
SECRET_KEY="$(kubectl -n rook-ceph get secret rook-ceph-object-user-fast-loki \
  -o jsonpath='{.data.SecretKey}' | base64 -d)"

kubectl -n monitoring create secret generic loki-s3 \
  --from-literal=LOKI_S3_ACCESS_KEY="$ACCESS_KEY" \
  --from-literal=LOKI_S3_SECRET_KEY="$SECRET_KEY" \
  --dry-run=client -o yaml | kubectl apply -f -
```

Alloy runs as a DaemonSet in the same namespace and reads pod logs through the
Kubernetes API, filtered to the node it runs on, so each log line is collected
once. Pod logs carry a `container` label in addition to `namespace`, `pod`,
`node` and `app`. Alloy also mounts the host `/var/log` read-only and collects
Talos service/kernel logs with `log_type="talos"` and the kube-apiserver audit
log with `log_type="audit"`. Talos has no journald; `/var/log/*.log` is the
equivalent. `tail_from_end = true` skips the historical contents of the current
files, so only new lines are ingested. The Loki chart's ServiceMonitor,
recording rules and dashboards are enabled; the dashboards land in the "Loki"
Grafana folder. Grafana has a Loki data source alongside Thanos.

Reconcile the separate logging Kustomization after monitoring:

```sh
./scripts/flux/manage.py reconcile monitoring logging
kubectl -n monitoring get pods -l app.kubernetes.io/name=loki
kubectl -n monitoring get pods -l app.kubernetes.io/name=alloy
```

View logs in Grafana at <https://grafana.glem.men/explore> with the `Loki` data
source, or use the "Loki / Logs" dashboard in the "Loki" folder. Useful queries:

- `{cluster="glemmen"}` — all pod logs
- `{namespace="monitoring", container="loki"}` — one container
- `{log_type="talos"}` — Talos host/service/kernel logs
- `{log_type="talos", filename="/var/log/kernel.log"}` — kernel only
- `{log_type="audit"}` — Kubernetes audit; add `| json` to query fields

The API server audit log is high-volume because the Talos audit policy records
most requests. Filter it by `verb` or `objectRef.resource` in Explore, or add a
`loki.process` drop stage if the volume becomes a problem.

Loki runs as a single binary with one replica. A restart briefly interrupts
ingestion and queries; Alloy retries while Loki is unavailable. This is the
deliberate non-HA logging setup.

## Grafana SSO

Grafana requires a login; anonymous Viewer access is disabled and the Homepage
dashboard links to the WAN panel instead of embedding it. The login page still
accepts the local `admin` account as a break-glass path, and shows an
"Authentik" button for SSO.

Create the Authentik OAuth2/OpenID provider and application by hand:

1. Create the group `Grafana Admins` and add the users who should be Grafana
   admins.
2. Create an OAuth2/OpenID provider named `Grafana` with client type
   `Confidential`, the signing key, the `openid`, `email` and `profile` scopes,
   and the redirect URI `https://grafana.glem.men/login/generic_oauth`.
3. Create the application `Grafana` with the slug `grafana`, bind it to the
   provider, and add a policy binding for the `Grafana Admins` group (or a
   broader group if all Authentik users should be able to view).
4. Create the `grafana-authentik` Secret in `monitoring` with the provider's
   client ID and secret.

```sh
kubectl -n monitoring create secret generic grafana-authentik \
  --from-literal=client-id='<client ID>' \
  --from-literal=client-secret='<client secret>' \
  --dry-run=client -o yaml | kubectl apply -f -
```

The `auth.generic_oauth.role_attribute_path` mapping in
`monitoring/kube-prometheus-stack/values.yaml` gives `Grafana Admins` the
Grafana `Admin` role and everyone else `Viewer`. The local admin account stays
server admin. Authentik's default `profile` scope returns the `groups` claim
used by the mapping. The redirect URI must match exactly.

## Alerts and notifications

Prometheus evaluates the `PrometheusRule` objects and sends firing alerts to
Alertmanager; Grafana is only used for dashboards and for displaying
Alertmanager alerts. Do not create Grafana-managed alert rules. The custom
rules live in `monitoring/resources/alerts/prometheus-rules.yaml`:

- `custom.storage` and `custom.certmanager` — PVC free space/inodes, Pending
  PVCs, the Prometheus 20 GB budget, and cert-manager certificate expiry.
- `custom.yugabyte` — master/tserver availability, YSQL read/write latency,
  TabletServer p99 latency, and RPC queue backlog.
- `custom.thanos` — sidecar upload failures, compactor halted, and Query/Store
  Gateway availability.

The controller-manager, scheduler and kube-proxy ServiceMonitors are disabled
because Talos binds those metrics to localhost; the corresponding default
alert groups are disabled in
`monitoring/kube-prometheus-stack/values.yaml`. `CPUThrottlingHigh` is
intentionally kept.

Alertmanager sends email through Gmail using the existing Authentik mail
account (`noreply@blalange.org` → `hexahigh0@gmail.com`). Only `critical`
alerts are emailed; warnings and info are routed to the `null` receiver and
remain visible in the Alertmanager UI. The SMTP password is
not in Git; create the `alertmanager-smtp` Secret in `monitoring` from the same
`AUTHENTIK_EMAIL__PASSWORD` value used by Authentik:

```sh
kubectl -n monitoring create secret generic alertmanager-smtp \
  --from-literal=auth-password='<Gmail app password>' \
  --dry-run=client -o yaml | kubectl apply -f -
```

The Alertmanager config mounts it at
`/etc/alertmanager/secrets/alertmanager-smtp/auth-password` and uses
`smtp_auth_password_file`, so rotating the password only requires updating the
Secret and restarting Alertmanager.

Alertmanager runs two replicas that gossip silences and notification state;
the read-only proxy also runs two replicas so the UI survives a pod or node
failure. Alertmanager is exposed at <https://alerts.glem.men>; the same URL is
set as `alertmanagerSpec.externalUrl` so notification links point there. The
ingress points at the nginx read-only proxy
(`monitoring/resources/alertmanager-proxy.yaml`) that forwards only `GET`,
`HEAD` and `OPTIONS` and returns `405` for `POST`/`PUT`/`PATCH`/`DELETE`, so
the UI cannot create or delete silences. The UI is still unauthenticated:
anyone who can reach it can view alerts.

## iDRAC hardware metrics

`monitoring/idrac-exporter` runs mrlhansen's Redfish exporter and Prometheus
scrapes it every minute for every iDRAC in VLAN 4. Prometheus passes the BMC
address as the `target` parameter, so the exporter is stateless. The target
list and the server-name relabeling live in
`monitoring/resources/scrapeconfigs/idrac-exporter.yaml`. The `BMC` and
`BMC overview` Grafana dashboards come from the upstream `grafana/` directory
and are refreshed by `scripts/update-grafana-dashboards.py`.

The exporter uses the read-only BMC account, which is stored in the
hand-created `idrac-exporter` Secret in `monitoring` (the same account as the
inventory collector):

```sh
kubectl -n monitoring create secret generic idrac-exporter \
  --from-literal=username=readonly \
  --from-literal=password=readonly \
  --dry-run=client -o yaml | kubectl apply -f -

./scripts/flux/manage.py reconcile monitoring monitoring-resources
```

The BMC list is not discovered automatically. When a server's `redfish_ip`
changes in `inventory/manual/devices/`, update the ScrapeConfig as well.

## Volunteer network services

`apps/volunteer` runs Tor Snowflake (3 replicas), a Syncthing relay, a Tor
WebTunnel bridge at `https://wt.glem.men/<secret path>` and a non-exit Tor
guard/middle relay. The WebTunnel path comes from the hand-created
`flux-system/volunteer-secrets` Secret and is substituted by Flux.

Public forwards via the UniFi router to `192.168.6.99`:

| Port | Service |
| --- | --- |
| TCP 22067 | Syncthing relay data |
| TCP 22070 | Syncthing relay status |
| TCP 9001 | Tor relay ORPort |

WebTunnel uses the existing 443 forward, and Snowflake needs no inbound ports.
The three small PVCs use `fast-rbd` with RF2. The stateful relay/bridge Deployments stay at one pod because
each owns a single long-term identity; only Snowflake runs three pods.

The Tor relay and Syncthing relay advertise the static WAN address
`109.247.229.146`; update both manifests (and the WebTunnel DNS record) if the
WAN address changes. If the Tor relay stays at "Bootstrapped 5%" or the
WebTunnel bridge at 45%, the upstream network is filtering Tor relay
destinations rather than the cluster services; check the ISP/UniFi threat
settings before changing the manifests.

## NetBox

`apps/netbox` runs NetBox at <https://netbox.glem.men> as a read-only
visualization of the network inventory. NetBox uses its own PostgreSQL and
Valkey instances in the `netbox` namespace; uploaded media uses a CephFS
`ReadWriteMany` volume. The inventory data lives in the repository-root
[`inventory/`](../inventory/README.md) directory; the collector, sync and
language server live in the separate
[netbox-inventory-toolkit](https://github.com/Blalange/netbox-inventory-toolkit)
repository. The `netbox-sync` CronJob runs the pinned toolkit image and
reconciles the inventory into NetBox every 10 minutes. The
`netbox-topology-views` plugin provides the cable/topology map at
<https://netbox.glem.men/plugins/netbox_topology_views/>. Every object
created by the job carries the `gitops` tag; pruning is enabled in the CronJob
and never touches objects created by hand. See `apps/netbox/README.md` for the
deployment and `inventory/README.md` for the site inventory and sync notes.

The Grafana database is documented in `infrastructure/yugabyte/README.md`. Its
role passwords are in `yugabyte-auth` (`yugabyte` namespace) and `grafana-db`
(`monitoring` namespace). NetBox keeps its own PostgreSQL and
`netbox-secrets`.

## Dependencies (was Fleet `dependsOn`)

- `infrastructure` (namespaces, cert-manager chart, external-dns, MetalLB, metrics-server, descheduler, YugabyteDB, NFD, GPU operator)
- `infrastructure` -> `rook-ceph` (Rook Ceph cluster, fast/NVMe pools, RGW and storage classes)
- `infrastructure` + `metallb-pool` -> `pxe` (proxyDHCP/TFTP chainloader + Talos boot assets)
- `infrastructure` + `rook-ceph` -> `media` (Jellyfin, *arr, Seerr, qBittorrent)
- `cert-manager-issuers` -> `cert-manager-certificates` -> `ingress` (Traefik)
- `infrastructure` + `rook-ceph` -> `monitoring` (kube-prometheus-stack -> Thanos) -> `monitoring-dashboards` / `monitoring-alerts`
- `monitoring` -> `logging` (Loki -> Alloy)
- `apps` waits for `infrastructure`, `monitoring` and `ingress`; the individual
  applications additionally wait for what they need (`homepage` for example
  waits for `homepage-assets`, `kube-prometheus-stack` and `infrastructure`;
  `netbox` waits for `infrastructure` and `monitoring`).

`external-dns` runs in the `cert-manager` namespace so it can reuse the
existing `cloudflare-api-token-glem-men` Secret. It only manages Services with
the `external-dns.kubernetes.io/hostname` annotation (the prefix used by
external-dns 0.23+) and uses `upsert-only`, so hand-managed records such as the
`*.glem.men` wildcard are never deleted.

The Minecraft Radar Bedrock server (`flux/apps/minecraft/radar`, resources
prefixed `minecraft-radar`) is pinned to `glemmen50`, `glemmen60` and
`glemmen80`. It uses NetherNet on custom ports: **TCP 19142** for signaling and
**UDP 19143-19158** for gameplay. Connect with `radar.mc.glem.men:19142`. UniFi
forwards both ranges to the shared MetalLB VIP `192.168.6.99`; the DNS record
is managed by external-dns.

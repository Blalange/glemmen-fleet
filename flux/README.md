# Flux

GitOps for the Talos cluster, replacing Fleet. Flux is bootstrapped into
`flux/clusters/glemmen/` and syncs everything from this repository.

## Layout

```
scripts/flux/
├── setup.py                    bootstrap Flux (GITHUB_TOKEN + KUBECONFIG)
└── manage.py                   status / sync / suspend / resume helpers

flux/
├── clusters/glemmen/           entry points, synced by the root Kustomization
│   ├── flux-system/            (generated by `flux bootstrap`)
│   ├── infrastructure.yaml     -> flux/infrastructure
│   ├── longhorn-backup.yaml    -> flux/infrastructure/longhorn/rclone (S3 bridge)
│   ├── cert-manager-issuers.yaml    -> cert-manager/issuers (chart -> issuers)
│   ├── cert-manager-certificates.yaml -> cert-manager/certificates (-> kube-system)
│   ├── ingress.yaml            -> flux/ingress (Traefik, depends on certificates)
│   ├── monitoring-pvc.yaml     -> kube-prometheus-stack/pvc (Grafana volume + SC)
│   ├── monitoring.yaml         -> flux/monitoring (KPS, Thanos, smartctl, iDRAC, unpoller)
│   ├── seaweedfs.yaml          -> flux/infrastructure/seaweedfs (S3 object store)
│   ├── monitoring-dashboards.yaml / monitoring-alerts.yaml
│   └── apps.yaml               -> flux/apps (application Kustomizations)
├── infrastructure/             namespaces, Longhorn, cert-manager, MetalLB, metrics-server, YugabyteDB, SeaweedFS operator, NFD
├── ingress/                    Traefik HelmRelease + values
├── monitoring/                 kube-prometheus-stack, Thanos, smartctl-exporter, idrac-exporter, unpoller
└── apps/                       Kustomization objects, Homepage, NetBox + inventory sync
```

The application manifests themselves stay in the repository root (`colibri/`,
`energisjappa/`, `frigate/`, `homepage/`, `panel/`, `snipe-it/`, `unifi/`,
`cert-manager/`, `kube-prometheus-stack/`) — the Flux Kustomizations point at
those directories. The old `fleet.yaml` files and the values files that moved
into `flux/` have been deleted.

Helm values live next to their HelmRelease and are turned into ConfigMaps with
`configMapGenerator`; the HelmRelease reads them through `valuesFrom`.

## Daily use

```sh
./scripts/flux/manage.py status                  # everything at a glance
./scripts/flux/manage.py sync                    # pull the latest Git revision now
./scripts/flux/manage.py reconcile homepage      # re-apply one Kustomization
./scripts/flux/manage.py apps-off                # suspend application workloads
./scripts/flux/manage.py apps-on                 # resume them
./scripts/flux/manage.py freeze / unfreeze       # suspend/resume everything
```

`flux reconcile` / `flux get` / `flux logs` also work directly if you prefer.
The pinned `flux`/`kubectl` binaries live in `scripts/bin/`; download them with
`./scripts/download-tools.py` (see `scripts/README.md`).

Tuppr's Talos/Kubernetes upgrade targets are generated from
`talos/settings.env`; use `./scripts/check-updates.py` to see available
Talos, Kubernetes, Flux, Helm and container-image updates.

## Longhorn backups (Google Drive via rclone)

Longhorn's S3 backupstore is provided by an in-cluster `rclone serve s3`
Deployment that exposes a Google Drive remote as S3. The backup target in
`infrastructure/longhorn/values.yaml` is `s3://longhorn-backup@us-east-1/`;
`longhorn-backup` is a folder in the Drive remote and is created by the bridge.

The bridge and Longhorn share one hand-created Secret in `longhorn-system`:

| Key | Value |
| --- | --- |
| `rclone.conf` | rclone config with a remote named `gdrive` |
| `AWS_ACCESS_KEY_ID` | S3 access key (any random string) |
| `AWS_SECRET_ACCESS_KEY` | S3 secret (any random string) |
| `AWS_ENDPOINTS` | `http://rclone-s3.longhorn-system.svc.cluster.local:9000` |

Create `rclone.conf` on a workstation with `rclone config` (remote name
`gdrive`, type Google Drive), set `use_trash = false` in that block so deleted
backup blocks do not pile up in the Drive trash, then create the Secret:

```sh
kubectl -n longhorn-system create secret generic rclone-backup-config \
  --from-file=rclone.conf=./rclone.conf \
  --from-literal=AWS_ACCESS_KEY_ID="$(openssl rand -hex 16)" \
  --from-literal=AWS_SECRET_ACCESS_KEY="$(openssl rand -hex 32)" \
  --from-literal=AWS_ENDPOINTS=http://rclone-s3.longhorn-system.svc.cluster.local:9000 \
  --dry-run=client -o yaml | kubectl apply -f -
```

Then reconcile Longhorn and the bridge:

```sh
./scripts/flux/manage.py reconcile infrastructure longhorn-backup
kubectl -n longhorn-system get pods -l app.kubernetes.io/name=rclone-s3
```

The target status is visible in the Longhorn UI under Backup and Restore >
Backup Targets (and `longhorn-manager` logs show S3 errors). The template is
`infrastructure/longhorn/rclone/rclone-backup-config.yaml.example`; the real
`rclone.conf` and filled-in Secret manifest are gitignored.

Once the target is healthy, re-create the recurring backup job(s) with a
retention policy that fits the Drive quota (Longhorn UI > Settings > Recurring
Jobs, or `RecurringJob` CRs with `task: backup` and `retain`).

Changing `rclone.conf` or the S3 keys in the Secret requires a restart of the
bridge (the init container copies the config once per pod):

```sh
kubectl -n longhorn-system rollout restart deploy/rclone-s3
```

If the Longhorn target reports an error, check
`kubectl -n longhorn-system logs deploy/rclone-s3`; an expired or revoked
Google token needs a new `rclone.conf` in the Secret and a rollout restart.

The `Longhorn Monitoring & Backups` Grafana dashboard is an enhanced local
copy based on Grafana.com dashboard 16888. It adds volume IOPS, throughput,
read/write latency, per-volume status tables and workqueue depth/latency/retry
statistics. Because it is now customized,
`scripts/update-grafana-dashboards.py` does not refresh it from upstream.

## SeaweedFS object storage

Long-term metrics live in a SeaweedFS cluster in the `seaweedfs` namespace. It
is managed by the SeaweedFS operator (Helm release `seaweedfs-operator`) and
exposed as S3 at `seaweedfs-s3.seaweedfs.svc.cluster.local:8333`. The operator
also installs CRDs for buckets, S3 identities, credentials and policies, so
future applications can request their own bucket and key pair next to their
workload.

The SeaweedFS resource, its master PVC and the `thanos` bucket/IAM objects are
in `infrastructure/seaweedfs/`. The `seaweedfs` Flux Kustomization depends on
`infrastructure` so the operator's CRDs exist before its custom resources are
applied.

The filer stores its metadata in the existing YugabyteDB cluster using the
`postgres2` store, so filer replicas can be restarted or scaled without losing
metadata. The `seaweedfs` role and database are created by the
`yugabyte-init-v1` Job in the `yugabyte` namespace. Its password is the
`seaweedfs-password` key in the `yugabyte-auth` Secret (created by hand, not in
Git; see `infrastructure/yugabyte/README.md`).

The filer's `seaweedfs-filer-config` Secret must carry the same password and the
new YSQL service name:

```sh
PW="$(kubectl -n yugabyte get secret yugabyte-auth \
  -o jsonpath='{.data.seaweedfs-password}' | base64 -d)"

kubectl -n seaweedfs create secret generic seaweedfs-filer-config \
  --from-literal=filer.toml="$(cat <<EOF
[postgres2]
enabled = true
createTable = true
hostname = "yb-tservers.yugabyte.svc.cluster.local"
port = 5433
username = "seaweedfs"
password = "${PW}"
database = "seaweedfs"
sslmode = "disable"
EOF
)" --dry-run=client -o yaml | kubectl apply -f -
```

The operator generates the `thanos` key pair in the `thanos-s3-credentials`
Secret in the `seaweedfs` namespace. Copy it into the hand-created
`thanos-objstore-config` Secret in `monitoring` (the secret is not in Git):

```sh
ACCESS_KEY="$(kubectl -n seaweedfs get secret thanos-s3-credentials \
  -o jsonpath='{.data.accessKey}' | base64 -d)"
SECRET_KEY="$(kubectl -n seaweedfs get secret thanos-s3-credentials \
  -o jsonpath='{.data.secretKey}' | base64 -d)"

kubectl -n monitoring create secret generic thanos-objstore-config \
  --from-literal=objstore.yml="$(cat <<EOF
type: S3
config:
  bucket: thanos
  endpoint: seaweedfs-s3.seaweedfs.svc.cluster.local:8333
  region: us-east-1
  access_key: ${ACCESS_KEY}
  secret_key: ${SECRET_KEY}
  insecure: true
  bucket_lookup_type: path
EOF
)" --dry-run=client -o yaml | kubectl apply -f -
```

Existing blocks in the old Google Drive `thanos` bucket are not visible through
SeaweedFS until they are copied. Before switching the secret, copy them with a
one-off rclone job that mounts `rclone-backup-config` (for `gdrive:`) and the
SeaweedFS credentials, for example:

```sh
rclone copy gdrive:thanos \
  ":s3,provider=Other,endpoint=http://seaweedfs-s3.seaweedfs.svc.cluster.local:8333,access_key_id=${ACCESS_KEY},secret_access_key=${SECRET_KEY},region=us-east-1,force_path_style=true:thanos" \
  --transfers 4 --checkers 4 --checksum --progress
```

Keep the old Drive bucket until the Grafana Thanos data source has been
verified against SeaweedFS. After changing the secret, restart the Prometheus
statefulset (so its Thanos sidecar re-reads the config) and the Thanos
Store/Compactor pods.

## Thanos and long-term metrics

Prometheus is capped at 15GiB of local TSDB blocks (`retentionSize` in
`monitoring/kube-prometheus-stack/values.yaml`), so its 20Gi PVC stays within
the 20GB usage budget. The Thanos sidecar uploads completed blocks to the
`thanos` bucket in SeaweedFS; the `thanos` HelmRelease runs Query, Store Gateway
and Compactor against the same bucket. Grafana uses the additional "Thanos"
data source as its default, because it serves both live Prometheus data and the
long-term blocks; the built-in Prometheus data source remains available for
local troubleshooting.

The Thanos component dashboards (Overview, Compact, Query, Query Frontend,
Store, Receive, Sidecar, Rule and BucketReplicate) live in
`monitoring/resources/dashboards/thanos/` and are refreshed by
`scripts/update-grafana-dashboards.py`. Node Exporter and UniFi Poller
dashboards live in sibling `node-exporter/` and `unifi/` directories. Their
ConfigMaps carry a `grafana_folder` annotation, and the Grafana sidecar plus
the file provider's `foldersFromFilesStructure` setting place them in
dedicated "Thanos", "Node Exporter" and "UniFi Poller" folders. The chart's
built-in Kubernetes-mixin and node-exporter-mixin dashboards get the same
annotation from the HelmRelease post-renderer. Dashboards without the
annotation stay at the root (General) level.

The SeaweedFS and YugabyteDB dashboards live in the sibling `seaweedfs/` and
`yugabyte/` directories. SeaweedFS metrics are enabled by `metricsPort: 9327`
on each component of the `Seaweed` resource; the operator then creates the
ServiceMonitors and labels the listeners with the component names the
dashboard expects. The operator's bundled Grafana 4.x dashboard is disabled
because it is out of date. The YugabyteDB dashboard is a trimmed copy of the
upstream one: YEDIS is disabled, and the ServiceMonitor drops every per-tablet
series (`table_id`) to avoid ingesting roughly 300k active series. The
remaining YB-Master and YB-TServer RPC metrics are relabeled to the
`rpc_latency_*` names the dashboard uses.

Create the `thanos-objstore-config` Secret from the SeaweedFS credentials (see
the SeaweedFS section above) before reconciling monitoring; otherwise the
Prometheus sidecar cannot start.

Then reconcile SeaweedFS and monitoring:

```sh
./scripts/flux/manage.py reconcile seaweedfs monitoring
kubectl -n seaweedfs get pods
kubectl -n monitoring get pods -l app.kubernetes.io/part-of=thanos
```

`PrometheusPVCAbove20GB` fires if the local volume stays above the budget.
The usual cause is the sidecar not uploading (check the `thanos` container in
the Prometheus pod) or the Prometheus retention update not being applied
(HelmRelease values are watched through the generated ConfigMap label).

The PVC of an existing cluster may already have been expanded beyond 20Gi;
Kubernetes cannot shrink it in place. The usage cap still applies. Recreating
it at 20Gi is a separate maintenance operation (stop Prometheus, delete the
PVC, let the StatefulSet recreate it) and only makes sense after the sidecar
has uploaded the local blocks that should be kept.

## iDRAC hardware metrics

`monitoring/idrac-exporter` runs mrlhansen's Redfish exporter and Prometheus
scrapes it every minute for every iDRAC in VLAN 4. Prometheus passes the BMC
address as the `target` parameter, so the exporter is stateless. The target
list and the server-name relabeling live in
`monitoring/resources/scrapeconfigs/idrac-exporter.yaml`. The `BMC` and
`BMC overview` Grafana dashboards come from the upstream `grafana/` directory
and are refreshed by `scripts/update-grafana-dashboards.py`.

The exporter uses the read-only BMC account, which is stored in the
hand-created `idrac-exporter` Secret in `monitoring` (the same account as the
inventory collector):

```sh
kubectl -n monitoring create secret generic idrac-exporter \
  --from-literal=username=readonly \
  --from-literal=password=readonly \
  --dry-run=client -o yaml | kubectl apply -f -

./scripts/flux/manage.py reconcile monitoring monitoring-resources
```

The BMC list is not discovered automatically. When a server's `redfish_ip`
changes in `inventory/manual/devices/`, update the ScrapeConfig as well.

## Volunteer network services

`apps/volunteer` runs Tor Snowflake (3 replicas), a Syncthing relay, a Tor
WebTunnel bridge at `https://wt.glem.men/<secret path>` and a non-exit Tor
guard/middle relay. The WebTunnel path comes from the hand-created
`flux-system/volunteer-secrets` Secret and is substituted by Flux.

Public forwards via the UniFi router to `192.168.6.99`:

| Port | Service |
| --- | --- |
| TCP 22067 | Syncthing relay data |
| TCP 22070 | Syncthing relay status |
| TCP 9001 | Tor relay ORPort |

WebTunnel uses the existing 443 forward, and Snowflake needs no inbound ports.
The three small PVCs use the `volunteer` Longhorn StorageClass with three
volume replicas. The stateful relay/bridge Deployments stay at one pod because
each owns a single long-term identity; only Snowflake runs three pods.

The Tor relay and Syncthing relay advertise the static WAN address
`109.247.229.146`; update both manifests (and the WebTunnel DNS record) if the
WAN address changes. If the Tor relay stays at "Bootstrapped 5%" or the
WebTunnel bridge at 45%, the upstream network is filtering Tor relay
destinations rather than the cluster services; check the ISP/UniFi threat
settings before changing the manifests.

## NetBox

`apps/netbox` runs NetBox at <https://netbox.glem.men> as a read-only
visualization of the network inventory. NetBox uses its own PostgreSQL and
Valkey instances in the `netbox` namespace; uploaded media uses a Longhorn
`ReadWriteMany` volume. The inventory data lives in the repository-root
[`inventory/`](../inventory/README.md) directory; the collector, sync and
language server live in the separate
[netbox-inventory-toolkit](https://github.com/Blalange/netbox-inventory-toolkit)
repository. The `netbox-sync` CronJob runs the pinned toolkit image and
reconciles the inventory into NetBox every 10 minutes. The
`netbox-topology-views` plugin provides the cable/topology map at
<https://netbox.glem.men/plugins/netbox_topology_views/>. Every object
created by the job carries the `gitops` tag; pruning is enabled in the CronJob
and never touches objects created by hand. See `apps/netbox/README.md` for the
deployment and `inventory/README.md` for the site inventory and sync notes.

The Grafana database is documented in `infrastructure/yugabyte/README.md`. Its
role passwords are in `yugabyte-auth` (`yugabyte` namespace) and `grafana-db`
(`monitoring` namespace). NetBox keeps its own PostgreSQL and
`netbox-secrets`.

## Dependencies (was Fleet `dependsOn`)

- `infrastructure` (namespaces, Longhorn, cert-manager chart, MetalLB, metrics-server, SeaweedFS operator, NFD)
- `infrastructure` -> `longhorn-backup` (rclone S3 gateway for Google Drive backups)
- `infrastructure` -> `seaweedfs` (SeaweedFS cluster, bucket and S3 credentials)
- `cert-manager-issuers` -> `cert-manager-certificates` -> `ingress` (Traefik)
- `infrastructure` -> `monitoring-pvc`; `infrastructure` + `seaweedfs` -> `monitoring` (kube-prometheus-stack -> Thanos) -> `monitoring-dashboards` / `monitoring-alerts`
- `apps` waits for `infrastructure`, `monitoring` and `ingress`; the individual
  applications additionally wait for what they need (`homepage` for example
  waits for `homepage-assets`, `kube-prometheus-stack` and `infrastructure`;
  `netbox` waits for `infrastructure` and `monitoring`).

## Migration notes

- The migration from K3s/Fleet is done: the secrets and Longhorn volumes were
  restored from the NFS backups (see the repository history for the backup and
  restore scripts), the load balancer IP moved to `192.168.6.99`
  (`flux/ingress/traefik/values.yaml`) and all workloads resumed.
- **Secrets are not in Git**; they live in the cluster only (restored from the
  old cluster: Cloudflare tokens, `grafana-admin`, `unpoller-unifi`,
  `homepage-grafana`, `frigate-secrets`, `energisjappa-secrets`, `colibri-secrets`,
  `snipe-it-db`, `snipe-it-app-key`, `warrior-http-auth`,
  `volunteer-secrets` and the TLS certificates in `kube-system`; created for
  the rclone bridge: `rclone-backup-config`; generated by the SeaweedFS
  operator: `thanos-s3-credentials` in `seaweedfs`; created by hand for Thanos:
  `thanos-objstore-config` in `monitoring`; created for NetBox:
  `netbox-secrets` in `netbox` (superuser, YSQL/Valkey passwords, Django secret
  and sync API token); created for the shared YugabyteDB: `yugabyte-auth` in
  `yugabyte` (superuser, Grafana and SeaweedFS role passwords) and `grafana-db`
  in `monitoring`; created for iDRAC metrics: `idrac-exporter` in
  `monitoring`).
- **Backup target**: Longhorn backs up to `s3://longhorn-backup@us-east-1/`,
  served by the in-cluster `rclone serve s3` bridge in
  `infrastructure/longhorn/rclone/`. The actual backupstore is a folder
  (`gdrive:longhorn-backup`) in Google Drive; the bridge is configured by the
  hand-created `rclone-backup-config` Secret in `longhorn-system` (see the
  "Longhorn backups" section above).
- The Rancher import installed `cattle-system` (kept) and
  `cattle-fleet-system` (Fleet removed on 2026-10-15 — Flux does the GitOps).
- Future services can share `.99` on other ports with MetalLB (`autoAssign` is
  off, see `metallb/pool.yaml`), or get their own address from the pool.
